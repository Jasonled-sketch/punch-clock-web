# 保固條款系統

對外的保固條款網頁 ＋ 機身 QR 標籤產生器。
目的：**在成交當下就把保固界線講清楚並留下公告紀錄**，避免日後為了運費、檢測費之類的衍生費用起爭執。

| 檔案 | 用途 | 對象 |
|---|---|---|
| `index.html` | 對外保固說明頁：年限、狀況判定、費用、送修流程、條款全文（摺疊）、FAQ | **客戶**（掃 QR 或給連結） |
| `label.html` | 產生貼在機身背面的 QR 標籤，可批次帶序號、直接列印 | 內部（出貨前貼標） |
| `terms.md` | 條款純文字版，貼報價單背面、合約附件、LINE 回覆用 | 內部 |
| `USLED保固條款_v2.8.pdf` | A4 完整版，可列印或傳給客戶 | 客戶 |
| `保固收費流程圖.png` | **一張圖講完收費**：三步＋「誰付錢」表，客戶問「為什麼收 300」直接丟這張 | 客戶（LINE） |
| `flow.html` | 流程圖的原稿，改完內容重新截圖即可 | 內部 |
| `qr.js` | 離線 QR 產生器（不依賴任何外部服務或 CDN） | 程式用 |

**網址**：https://jasonled-sketch.github.io/punch-clock-web/warranty/

## 上線前必做的四件事

### 1. 補上公司聯絡資訊

`index.html` 頁尾的 `<span id="ftContact">` 目前只寫「高雄市岡山區　│　服務電話：請洽您的承辦業務或官方 LINE」。
請改成正式的**公司地址、電話、統一編號**——消費者保護法第 25 條規定保證書應載明製造商名稱與地址，這欄空著會讓整份文件的正式度打折。

公司名稱一律寫 **譽昇科技有限公司**（品牌 USLED）。

### 2. 確認費率

運費 NT$150 起、檢測費 NT$300、保管費 NT$50–450／日都已填入。**只剩「到府／到車行出勤費」仍寫「車馬費＋現場工時」沒有數字**，建議訂一個起跳價（例如市區 NT$800 起／趟），不然業務每次報價都要現場心算，客戶也會覺得你在看人喊價。

### 3. 確認管轄法院

條款第十三條寫的是**臺灣橋頭地方法院**（岡山區的管轄法院）。
若公司登記地不在岡山，請改成正確的地院。

### 4. 印標籤前實掃

打開 `label.html` → 填序號 → 產生 → **列印前先拿手機掃一次**，確認能開啟條款頁再大量印製。

## 日常怎麼用

### 業務成交時

1. 報價單上加一行：「本產品保固依 USLED 保固條款 v2.8，詳見機身 QR Code 或 〈網址〉。」
2. 把連結傳給客戶一次，並在 LINE 對話留下紀錄（這就是「已告知」的證據）。
3. 客戶是自然人消費者時，**一定要給滿 5 天審閱期**，不要當場逼單。

**成交當下一定要講的三句話**（講完客訴會少一半）：

> 「保固一年，US 的主機板五年。**只要是硬體壞掉，零件跟工資我們全免。**」
> 「送修的運費要您自己出，來回都是，這個保固內外都一樣。」
> 「機器如果整台不亮，**先打給我們**，通常是設定問題，講一下就好，不用寄回來花錢。」

### 出貨前

1. `label.html` 批次產生標籤（序號一行一個，**記得填品牌與出廠日**），列印在**合成紙／PET 防水標籤**上。
   出廠日會寫進 QR，客戶掃描後就能看到這台的出廠日與推定保固到期日，單據遺失也查得到。
2. 貼在機身背面靠近電源線出口處，避開會被支架遮住、被水柱直沖的面。
3. 貼上後實掃一次再出貨。

### 客戶報修時

先問三件事，很多狀況電話裡就能解決，不用拆機：

1. 機身序號、出貨日期（判斷在不在保固期內；**掃機身 QR 就能看到出廠日**）
2. **請客戶拍整片畫面的照片或影片**
3. 最近有沒有洗車、擦撞、換電瓶、自己拆過

**「整台都不亮」一定要先擋下來**——十次有八次是關屏或自動開關機設定。電話裡解決，客戶一毛都不用付。

真的要寄回來，照這個順序講：

> 「這台還在保固內，**只要驗出來是硬體壞掉，零件跟更換工資我們全免**。
> 送回來會有一筆 **300 元檢測費，這個保固內也要收**——就像看醫生要掛號費，
> 我們要拆箱錄影、拍照、確認有沒有外力水損、一片一片點亮、出檢測報告，這些工不管結果都要做。
> 保固保的是零件跟工資，檢測是另一件事。
> 運費來回您自己出。正常 3 到 5 個工作天，急件 1 到 3 天加急件費。」

**先講免費的，再講要收的。** 然後直接把 `保固收費流程圖.png` 丟過去，一張圖比十句話有用。

### 客戶還是不接受運費時

不要吵「規定就是這樣」，改用買車來比喻，這個每個人都懂：

> 「這就像您買一台新車，車子在保固期內引擎出問題，原廠免費幫您修；
> 但如果您開到台東拋錨，**把車拖回原廠的拖吊費，原廠不會幫您出**。
> 保固保的是產品本身的品質，不是把產品運回來的成本。
> 我們這邊也一樣：**零件跟工資我們扛到底，一毛不收；運送的成本各自負擔。**」

然後把條款連結傳過去，指**第五條**給他看，並把當初傳連結給他的 LINE 對話截圖一併附上。

### 客戶說「保固內為什麼還收檢測費？」

**不要吵「有沒有壞」。** 講兩件事是分開的：

> 「保固保的是**零件跟更換工資**——硬體真的壞了，這兩項我們一毛不收。
> 但檢測是另一項工作。您的機器寄來多半沒說清楚哪裡有問題，我們要拆箱錄影、拍照記錄外觀、
> 確認有沒有外力或水損、一片一片跑三色點亮、出檢測報告，這些不管結果都要做。
> 就像看醫生有掛號費，車子保固換引擎檢測費也照收，手機送修中心也是先收檢測費。
> **固定 300，不會因為多測幾項就多收**，而且已經包含拆裝跟更換的工時，不會再另外收工資。」

**三種情況免檢測費，主動講**：新品 30 天內、先打電話就遠端解決、同一故障 30 天內再送修。

**運費有三級，講清楚**：新品 7 天內我們全付；新品 8–30 天和二次送修「各付一趟」（寄來你付、寄回我們付）；其他都客戶付。

### 客戶問「那換模組的工錢呢？」

> 「**保固期內不另收工資，那 300 檢測費裡面就包含拆裝跟更換的工時了。**
> 只有保固期外才會另外算零件費跟更換工資，而且會先開報價單給您看，
> 您同意我們才動手，不會修完才跟您收錢。」

### 客戶說「有幾顆燈不亮，你們要免費修」

> 「LED 在製程上本來就允許極少數燈珠失效，業界通則是抓**千分之三**。
> 我們會實際數給您看：**超過千分之三，或者雖然沒超過但已經明顯影響辨識，那就算故障，保固內免費修**。
> 沒超過又看不太出來的，那是 LED 的正常範圍，全世界的廠商都一樣。
> 檢測過程我們全程有錄影，數字怎麼來的您可以調影片看。」

**不要跟客戶講「缺一撇」**——那是主觀判斷，講了就是替自己製造爭議。一律用可驗證的四種描述：整片不亮、行列條波異常、區塊顯示異常、明顯色偏。

## 修改條款的做法

條款內容存在兩個地方，**改動時務必兩邊同步**：

- `index.html` 的 `<section id="terms">` 區塊（客戶實際看到的）
- `terms.md`（紙本與 LINE 用）

改完之後：

1. 更新 `index.html` 裡的 `TERMS.version` 與 `TERMS.effective`（在頁面底部的 `<script>` 開頭）。
2. 同步更新 `terms.md` 開頭的版本與生效日。
3. 舊客戶適用**購買當時**的版本（條款第十二條第一項），**不溯及既往**，所以舊版不要刪掉——請另存為 `terms-v<舊版號>.md` 與 `USLED保固條款_v<舊版號>.pdf` 留檔。

## 放到官網上

`index.html` 是一個獨立完整的頁面，直接複製到官網目錄即可，沒有任何外部相依。

**如果官網本身已有導覽列**，在網址加上 `?embed=1` 會隱藏本頁自己的 sticky 導覽列，避免兩條導覽疊在一起：

```
https://你的官網/warranty/?embed=1
```

機身 QR 的網址也可以一併帶其他參數（順序不拘）：

| 參數 | 意義 | 例 |
|---|---|---|
| `sn` | 機身序號 | `?sn=A2609001` |
| `mo` | 型號 | `&mo=UM4C-3216` |
| `b` | 品牌（US 會顯示 5 年主機板保固） | `&b=US` |
| `d` | 出廠日 | `&d=2026-03-01` |

帶了參數，客戶掃進來頁面最上方會出現「本機資訊」卡，顯示序號、型號、出廠日與推定的保固到期日。

## 為什麼沒有線上簽署

因為客戶多半不會簽，而且很多是經銷商賣出的，根本沒機會當面簽。

所以自 v2.1 起改用**「購買即視同同意」**的架構（條款第一條）：條款公告在機身 QR、網頁與出貨文件上，客戶買了、收了貨就視同同意，有異議請在 7 天內提出。這在 B2B 與經銷通路是通行做法，也避開了「拿不到簽名 = 沒有依據」的死結。

要讓這個架構站得住腳，**出貨時務必做到兩件事**：

1. **機身一定要貼 QR 標籤**（條款的公告管道，缺了這個「已公告」就說不通）
2. **出貨文件上加註一行**：「本產品保固依 USLED 保固條款 v2.8，詳見機身 QR Code 或 〈網址〉。」

日後若還是想要簽名存證（例如大單、客製案），線上簽署的程式碼在 git 歷史裡（v2.0 版本的 `index.html`），可以隨時取回加裝。

## qr.js 技術說明

自行實作的 QR 產生器，**不依賴任何外部服務或 CDN**（列印標籤的電腦離線也能用，且不會把序號送到第三方伺服器）。

```js
const qr = QRLite.make('https://example.com/', 'M');  // 回傳 {version, size, modules, mask, ecLevel}
QRLite.toSVG(qr, {quiet: 2});                          // SVG 字串
QRLite.toCanvas(canvasEl, qr, {scale: 8});             // 畫到 canvas
```

- 支援 Byte mode（UTF-8）、version 1–10、錯誤更正 L／M／Q／H
- 自動選版本、自動選最佳 mask（依 ISO/IEC 18004 的四條懲罰規則）
- 開發時以 `jsqr` 解碼器做過 550 筆隨機字串驗證，version 1–10 × 四種錯誤更正等級全數通過
- 內容超過 version 10 容量會丟出錯誤；標籤網址請保持簡短

修改 `qr.js` 後請重新驗證：產生幾張標籤 → 手機實掃 → 確認能開啟正確網址。
