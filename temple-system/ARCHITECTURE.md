# 宮廟雲：系統架構

一套程式，四個方案。方案只決定「開哪些功能、資料放哪裡」，櫃台操作畫面一致，升級不用重新教學。

## 1. 宮廟類型 × 組織型態 × 章程

| 類型 | 常見對象 | 可選組織型態（預設在前） | 產出文件 |
| --- | --- | --- | --- |
| 祠 | 宗祠、家廟 | 派下員大會制（祭祀公業）、管理人制 | 規約／章程 |
| 堂 | 齋堂、鸞堂、佛堂 | 管理委員會制、管理人制、一貫道管理委員會制 | 組織章程 |
| 壇 | 神壇、私人壇 | 管理人制、管理委員會制 | 組織章程 |
| 宮 | 道教、民間信仰 | 管理委員會制、管理人制、信徒大會制 | 組織章程 |
| 寺 | 佛教寺院 | 執事會制（住持）、信徒大會制 | 組織章程 |
| 殿 | 道教、民間信仰 | 管理委員會制、管理人制、信徒大會制 | 組織章程 |

- **有委員會**：管理委員會制、信徒大會制、執事會制、派下員大會制。
- **沒有委員會**：管理人制，由管理人一人負責，重大事項開信徒會議。
- 章程骨架依內政部五種「非財團法人制寺廟組織或管理章程範例」，涵蓋寺廟登記應記載的 12 個事項。祠堂屬祭祀公業者，依祭祀公業條例改稱「規約」。
- 每份章程同時附一份 **〈香油及點燈收入管理辦法〉**，內容就是本系統的作業流程：當場開收據、不得跳號、作廢留號、每日兩人點收、月報、公開姓名遮一字、備份。**廟方採用章程，等於採用我們的系統流程。**
- 程式：`charter.js`（`TEMPLE_TYPES`、`ORG_TYPES`、`buildCharter()`、`buildRules()`）。

> 範本僅供參考，送件前需經所在地民政單位確認。

## 3. 部署架構

```mermaid
flowchart LR
  subgraph 廟內
    PC[櫃台主機<br>PWA＋收據印表機]
    LED[字幕機<br>HDPlayer／HD2020／C-Power]
    TV[電視牆<br>Android 電視盒]
  end
  subgraph 雲端（標準以上）
    API[API＋資料庫]
    GW[字幕機閘道]
    SMS[簡訊閘道]
    JOB[排程：自動提醒・月報（豪華以上）]
    SYNC[LINE・FB・官網同步（旗艦）]
  end
  PC -- 入門：只存本機 --> PC
  PC -- 標準以上 --> API
  API --> GW --> LED
  API --> TV
  API --> SMS
  JOB --> SMS
  API --> SYNC
```

- **入門**：主機裝好 PWA，資料存在本機，每週備份到隨身碟（寫在管理辦法裡）。
- **標準以上**：同一套前端，把 `store` 換成雲端 API，資料每日自動備份。
- **字幕機**：灰度全彩卡可設定成主動連回雲端閘道，廟裡不必放電腦；單雙色卡或舊卡則在廟裡放樹莓派中繼。電視牆直接開網頁。

## 4. 資料模型（原型）

- `temple`：名稱、類型、組織型態、主神、地址、負責人、章程參數
- `records`：收據編號（民國年月日-流水號）、日期、信眾、手機、地址、項目、數量、金額、是否公開、作廢
- `led`：播報佇列
- `sms`：推播紀錄
- `rules`：全自動開關
- `events`：建醮（職稱、斗首、認捐）
- `troupes`：陣頭

## 5. 下一步

1. 後端：選定雲端資料庫與 API，把 `load()`、`save()` 換成 API 呼叫，並加上帳號權限。
2. 字幕機閘道：先做灰度全彩卡的 `UpdateProgram`，需要實體控制卡測試。
3. 收據格式：依廟方現用的收據尺寸（三聯單、A5、熱感紙）調整列印版面。
4. 章程：由民政或法律專業人士審閱範本後，再作為正式產品內容。
5. 簡訊閘道、LINE 官方帳號串接。

## 執行
